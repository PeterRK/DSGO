# AVL Trees
　　Trees are suitable for search, but to obtain good performance (`O(logN)` time), the distances from the root to the leaves cannot vary too much. Trees satisfying that requirement are called balanced trees, and the AVL tree discussed here is one of the most classical examples.
```go
type node[T cmp.Ordered] struct {
    key    T
    state  int8        //balance factor
    parent *node[T]
    kids   [2]*node[T] //Left and Right are 0 and 1 respectively
}
```
　　An AVL tree adds a balance factor to each node, recording the difference between the height of the right subtree (the greatest distance from the node to a leaf) and the height of the left subtree. When the absolute value of the balance factor does not exceed one, the tree is considered balanced.

　　So an AVL tree does not directly store subtree heights. It stores only "how far apart the two sides are." That makes local repair more direct and compresses the balancing condition into a very small piece of local information.

## Rebalancing
　　The key to an AVL tree is maintaining balance. When balance is lost, a rebalancing transformation must be performed. If we stay vigilant enough, then whenever the tree becomes unbalanced there will be exactly one node whose balance factor is either `-2` or `2`. Looking at the balance factor of its child then yields four cases in total. By symmetry, we only need to analyze two of them in practice: the LL case and the LR case.

　　Below we show how the (rotation) transformation is performed:
```
---------------LR--------------    ---------------LL---------------
|       G       |       C       |    |       G       |       P       |
|      / \      |      / \      |    |      / \      |      / \      |
|     P         |     P   G     |    |     P         |     C   G     |
|    / \        |    / \ / \    |    |    / \        |    / \ / \    |
|       C       |      u v      |    |   C   x       |        x      |
|      / \      |               |    |  / \          |               |
|     u   v     |               |    |               |               |
```
　　Except for the pseudo-LL case (and symmetrically pseudo-RR), the transformation lowers the height of the subtree.
```go
func (G *node[T]) rotate() (*node[T], bool) {
    Pside := (G.state + 2) / 4           //G.state == -2 || G.state == 2
    Uside := 1 - Pside
    P := G.kids[Pside]
    if direct := G.state / 2; P.state == -direct {  //LR(RL)
        C := P.kids[Uside]                          //C != nil
        P.kids[Uside] = P.Hook(C.kids[Pside])
        G.kids[Pside] = G.Hook(C.kids[Uside])
        C.kids[Pside], C.kids[Uside] = C.hook(P), C.hook(G)
        G.state, P.state = 0, 0
        if C.state == direct {
            G.state = -direct
        } else if C.state == -direct {
            P.state = direct
        }
        C.state = 0
        return C, false
    } else {                                        //LL(RR)
        G.kids[Pside] = G.Hook(P.kids[Uside])
        P.kids[Uside] = P.hook(G)
        if P.state == direct {                      //true LL(RR)
            G.state, P.state = 0, 0
            return P, false
        } else {                                    //pseudo LL(RR), keep height
            G.state, P.state = direct, -direct
            return P, true
}   }   }
```
　　A rotation is not a complete new search through the tree. It is merely a local rewiring of a small number of parent-child relations. That is exactly why the structural cost of a single rotation is `O(1)`.

## Insertion & Deletion
　　Insertion may break balance, though it never produces the pseudo-LL case (or pseudo-RR). In that situation, one rotation plus a number of balance-factor adjustments (`O(logN)` in total) is enough to restore balance.
```go
func (tr *Tree[T]) rebalanceAfterInsert(root *node[T], trace uint64) {
    for {
        state := root.state
        root.state += int8(trace&1)*2 - 1   //adjust the balance factor (trace records the search path)
        if state == 0 {                     //root.state becomes -1 or 1
            if root.parent != nil {
                root = root.parent          //cascade upward
                trace >>= 1
                continue
            }
        } else if root.state != 0 {         //root.state becomes -2 or 2
            super := root.parent
            root, _ = root.rotate()         //rebalance transformation (the subtree height must fall, so stop here)
            if super == nil {
                tr.root = super.hook(root)
            } else {
                super.kids[(trace>>1)&1] = super.hook(root)
        }   }
        break                               //root.state is 0, nothing more to do
}   }
```
　　Deletion may also break balance. Because a rotation may lower the subtree height, one rotation is not always enough to solve the problem. So the number of transformations and the number of balance-factor adjustments may both reach `O(logN)`.
```go
func (tr *Tree[T]) rebalanceAfterRemove(root *node[T], trace uint64) {
    state, stop := root.state, false
    root.state -= int8(trace&1)*2 - 1
    for state != 0 {                        //if the old balance factor is 0, subtree height stays unchanged
        super := root.parent
        if super == nil {
            if root.state != 0 {            //root.state is -2 or 2
                root, _ = root.rotate()
                tr.root = super.hook(root)  //rebalance transformation
            }
            break
        }
        if root.state != 0 {                //root.state is -2 or 2
            root, stop = root.rotate()
            super.kids[(trace>>1)&1] = super.hook(root)
            if stop { break }               //subtree height unchanged, stop tracing upward
        }
        root, state = super, super.state    //cascade upward
        trace >>= 1
        root.state -= int8(trace&1)*2 - 1
}   }
```
　　This is also the difference between insertion and deletion: insertion usually just creates one "bulge" along a path, whereas deletion is more like pulling away a segment of support, and the effect may propagate upward all the way to the top.

## Performance Analysis
　　So far we have taken for granted that AVL trees are balanced. Now let us see how balanced they really are:
```
Let l(n) be the maximum tree height when the shortest path in the tree is n, then l(n+1) = l(n) + 2
                        X
l(n+1) = Depth {       / \     } = l(n) + 2
                 l(n)+1   l(n)
Clearly f(1) = 2, and by induction we get l(n) = 2n
```
　　That is, the length of the longest path never exceeds twice the length of the shortest path, and therefore even in the worst case the search time for a single node remains at the `O(logN)` level.
```
Let f(n) be the minimum number of nodes required to build an AVL tree of height n, then
f(n+1) = f(n) + f(n-1) + 1
From this we can derive f(n) ≈ 2^((log(√5+1)-1)n) ≈ 2^(n/1.44)
```
　　From that we get a more precise conclusion: the longest possible path in an AVL tree is about `1.44log(N)`.

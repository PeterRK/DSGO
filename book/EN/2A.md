# Sorting Linked Lists
　　Sometimes we also want an ordered linked list, and then sorting is required.

## Merge Sort

　　A linked list cannot be randomly accessed the way an array can, so splitting it takes extra effort. On the other hand, merging linked lists needs no extra buffer, so merge sort on a linked list can achieve `O(1)`-level auxiliary space.
```go
func mergeSort[T cmp.Ordered](list *ll.Node[T]) (head, tail *ll.Node[T]) {
    head, tail = list, ll.FakeHead(&head)
    size := 0
    for ; list != nil; size += 2 {             //probe the size first
        if list.Next == nil {
            tail = list
            size++
            break
        }
        a, b := list, list.Next
        list = b.Next
        if a.Val > b.Val {
            tail.Next, b.Next, a.Next = b, a, list
            tail = a
        } else {
            tail = b
    }   }
    for step := 2; step < size; step *= 2 {
        list, tail = head, ll.FakeHead(&head)
        for list != nil {
            lst1 := list
            lst2 := cut(lst1, step)             //cut one segment of size at most step
            list = cut(lst2, step)              //cut the second segment
            var node *ll.Node[T]
            tail.Next, node = merge(lst1, lst2) //merge them
            tail, node.Next = node, list
    }   }
    return head, tail
}
```
　　On arrays, merging usually means moving elements into an extra buffer. On linked lists, it means reconnecting the `Next` pointers of nodes. The elements themselves never change residence, and that is exactly where linked-list merge sort gains its space advantage.

　　Because it splits first and merges later, merge sort has to traverse the list twice in each round of processing, which makes it slightly slower than quicksort.

## Introsort

　　Median-of-three random sampling is hard to implement cleanly on a linked list, and quicksort on a list is therefore more likely to fall into its worst case. For that reason, introsort is a more reasonable choice.
```go
func introSort[T cmp.Ordered](list *ll.Node[T], life uint) (head, tail *ll.Node[T]) {
    head, tail = sort2(list)
    if head == nil {
        if life == 0 {
            head, tail = mergeSort(list)        //call in a helper
        } else {
            lst1, pivot, lst2, _ := partition(list)
            head, tail = introSort(lst1, life-1)
            tail.Next = pivot                   //stitch front and back
            pivot.Next, tail = introSort(lst2, life-1)
    }   }
    return head, tail
}
```
　　The idea is the same as in the array version: exploit quicksort's average performance when things go well, but once recursion becomes too deep, hand the remaining work over to the steadier merge sort.

## Radix Sort

　　Just as with merge sort, radix sort is in some sense easier to implement on linked lists than on arrays, and it needs very little extra space.
```go
func RadixSort[T constraints.Integer](head *ll.Node[T]) *ll.Node[T] {
    //...
    const bk = 1 << 8
    parts, tails := new([bk]*ll.Node[T]), new([bk]*ll.Node[T])
    for step := uint(0); step < bitWidth; step += 8 {
        for i := 0; i < bk; i++ {
            parts[i] = nil
            tails[i] = ll.FakeHead(&parts[i])
        }
        for node := head; node != nil; node = node.Next {
            radix := uint8(node.Val >> step)
            tails[radix].Next, tails[radix] = node, node
        }
        tail := ll.FakeHead(&head)
        for i := 0; i < bk; i++ {
            if parts[i] != nil {
                tail.Next = parts[i]
                tail = tails[i]
        }   }
        tail.Next = nil
    }
    //...
    return head
}
```
　　In each round, nodes are split into small chains according to the current byte and then reconnected to the main chain in order. The whole process is therefore mostly pointer rewiring, so compared with the array version it feels more like "shuffling cards" than "moving cargo."
